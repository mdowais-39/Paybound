- **Catalog dataset: Amazon Berkeley Objects** (public AWS Open Data, no login) as the storefront spine — unblocks Phase 1 immediately. Flipkart (₹-priced, needs Kaggle) may be added later for demo optics.

Agent Orchestrator + Explanation service will target a `gemini-flash` model (fast, strong tool-calling). Integration kept **provider-agnostic** (single LLM-client abstraction keyed on `LLM_PROVIDER`) so we can swap to Anthropic Claude for the final demo recording (thematic fit with Razorpay's NPCI+Anthropic pilot) if a little credit is added. Not needed until Phase 6.
- **Telemetry gotcha found & fixed (Phase 0):** `tower-http`'s `TraceLayer` emits its request span at DEBUG level, which the default env-filter (`info,paybound=debug`) drops for non-`paybound` targets — so no span reached the collector. Fixed by instrumenting request handlers at INFO (`#[tracing::instrument(level = "info")]`) so exported traces don't depend on tower-http's span level. Verified end-to-end: gateway → OTLP → collector → Tempo (trace queryable, `rootServiceName=paybound-gateway`).

## Phase 1 — Data layer & audit ledger

- **Postgres port clash → host 5433.** A local `postgresql-x64-17` Windows service already owns 5432, so host→`localhost:5432` hit that instance (no `paybound` user) and auth-failed. Remapped the container to publish host **5433** (`5433:5432`); container-internal 5432 unchanged, so Temporal's internal link is unaffected. `DATABASE_URL` and defaults updated to 5433.
- **pgvector image collation quirk.** `pgvector/pgvector:pg16`'s `template1` reports a glibc collation-version mismatch, which blocks `CREATE DATABASE` (used by `#[sqlx::test]` per-test DBs). Fixed with a one-time `ALTER DATABASE template1 REFRESH COLLATION VERSION;` locally, and a best-effort CI step (`|| true`, no-op when versions already match on the Linux runner).
- **Compile-time-checked SQL + offline cache.** All ledger queries use `sqlx::query!`/`query_scalar!` (malformed SQL fails at build). The `.sqlx` offline cache is committed and regenerated with `cargo sqlx prepare --workspace -- --all-targets` (the `--all-targets` is required to capture `query!` macros inside test files). CI builds with `SQLX_OFFLINE=true` (no DB needed to compile) and runs the integration tests against a Postgres **service** container.
- **Audit timestamp folded as unix-microseconds (i64), not RFC3339.** Postgres `timestamptz` truncates to microseconds; hashing an integer derived from `unix_nanos/1000` round-trips exactly on read, whereas a formatted string could drift on the nanos→micros boundary and break `verify_chain` on a legitimate chain.
- **ABO catalog prices are SYNTHESIZED (honesty note).** Amazon Berkeley Objects has real titles/categories/brands/colours/variants but **no price**. Prices are generated per category from plausible ₹ ranges, deterministically seeded per `item_id` so re-runs are stable. Stated in the ingestion script header and here. 1000 items ingested across 144 categories (₹439–₹14,356). The first shard skews toward one category family (phone cases); may balance the sample across shards in Phase 3 when search relevance matters.

## Phase 2 — Mandate & Consent Kernel (crown jewel)

- **Kernel is pure, zero-I/O.** The `kernel` crate has no sqlx/tokio/network deps at all — `evaluate(cart, mandate, running_spend, now)` takes only data and returns `Approved(Authorization) | Refused(RefusalReason)`. The Reserve-Pay ledger read happens outside and `running_spend` is passed in, keeping the gate exhaustively testable (Part F #1).
- **`RequiresHumanAFA` is a `RefusalReason` whose `verdict()` maps to `needs_human`.** This keeps the prompt's exact 8-variant enum while producing the correct DB verdict: the ₹15,000 AFA case routes to human approval, all other reasons are hard `refused`.
- **Deterministic check order:** signature → TTL → cart integrity → category → merchant → per-txn cap → cumulative budget → AFA. The cited reason is always the most fundamental failure, which makes the refusal explainable.
- **Empty allow-list = unrestricted on that axis** (documented, not a loophole): an empty `allowed_categories`/`allowed_merchants` imposes no filter, but the amount caps and TTL still bind every purchase.
- **Cart integrity = recomputed-total match + optional expected-hash.** The kernel re-derives the total from line items (rejects a lying `total_paise`) and, when an `expected_cart_hash` is supplied, requires the cart hash to match exactly (the price-drift / item-substitution scenario for Phase 11).
- **ed25519 types re-exported from `common`** (`Ed25519SigningKey`/`VerifyingKey`) so `domain` names the crypto types through `common` rather than taking a second direct dalek dependency.

## Phase 3 — MCP Storefront server

- **MCP surface = axum JSON-RPC 2.0 over HTTP POST** (`initialize`/`tools/list`/`tools/call`), not the Rust MCP SDK. A single POST endpoint returning `application/json` is valid MCP Streamable-HTTP for non-streaming tool calls, is trivially testable with curl, and keeps the tool *semantics* in `Storefront` (SDK-swappable seam). Chosen per the prompt's Phase 3 risk note to avoid sinking time in an immature SDK.
- **`checkout` is the architectural heart: it never pays.** It reconstructs the exact cart from the persisted Cart Mandate, calls `kernel::evaluate`, writes a `gate_decision` + hash-chained audit entry, transitions the session (AUTHORIZED/NEEDS_HUMAN/REFUSED), and returns the decision. The agent has no tool that moves money.
- **Real bug caught by integration test (mandate_id).** `create_intent_mandate` originally let Postgres generate a fresh `mandate_id`, but the ed25519 signature is over the *signed* `mandate_id`; on reconstruction the ids differed and every signature failed → spurious `SignatureInvalid` refusals. Fixed by persisting the given `mandate_id` (it is part of the signed envelope). Exactly the seam bug the "integrate early" discipline exists to surface.
- **`create_cart` prices come from the catalog, never the agent.** The agent passes item ids + quantities; the storefront looks up price/category/merchant from the DB and enforces single-merchant carts.
- **Discovery surface:** `/.well-known/agents.txt` (robots-style pointer), `/.well-known/ard.json` (ARD manifest declaring tools + the signed-Intent-Mandate authority required), `/feed.json` (OpenAI/Google-style feed, prices in minor units), `/schema/{id}` (schema.org Product/Offer JSON-LD).
- **`examples/seed_demo.rs`** creates a signed mandate + bound session against the real catalog — reused for the HTTP smoke test now and the Phase 5 walking skeleton.

## Phase 4 — Execution plane + Razorpay

- **Payment path = Payment Links.** Probed the account: S2S UPI create (`/payments/create/upi`) returns 404 (not enabled), so an automated PIN-less UPI charge isn't available. Payment Links ARE real, dashboard-visible, payable objects — so execution creates a real link and completion is driven by the real `payment_link.paid` webhook (live) or a correctly-HMAC-signed synthetic event (automated tests). Stated openly.
- **Idempotency via DB-first claim, not Redis-only.** `authorize` does `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING` to atomically claim the key *before* creating the link — so a retry never creates a second link or double-charges, and there are no orphan links from a lost race. This is stronger than the prompt's Redis-only design; a Redis read-through cache is deferred to Phase 10. Verified live (same link on retry, `deduplicated=true`) and in tests.
- **`PaymentGateway` trait** decouples execution from the network: real `RazorpayClient` impl for production, a fake for deterministic tests (idempotency, paid/failed handling).
- **Webhook HMAC verified against the RAW body** (axum `Bytes` extractor, never re-serialized), constant-time compare via HMAC `verify_slice`. Bad signature → 401.
- **Gateway refactored to lib+bin** so the webhook receiver is testable via `tower::oneshot`.
- **Delegated token** = random 32-byte hex, scoped to one `payment_effect` (single-use); reuse is blocked by idempotency. This is the Shared-Payment-Token pattern (our own token, not a Razorpay recurring token).
- **No Razorpay `revoke_token`/AutoPay.** AutoPay recurring needs account enablement + a mandate-approval flow. Our revocation is at our own layer (Intent Mandate + Reserve-Pay ledger), which is where "kill the authority" actually lives in this architecture.
- **Live webhook delivery is a joint step:** to have the REAL `payment_link.paid` webhook reach the local gateway, a tunnel (cloudflared/ngrok) + a dashboard webhook with `RAZORPAY_WEBHOOK_SECRET` must be configured. The receiver logic itself is fully proven with signed synthetic events.

## Phase 5 — Walking skeleton (milestone)

- **Dedicated `harness` bin crate** (`walking-skeleton`) wires the real storefront + execution + ledger into one command. It's also the natural home for the Phase 11 scenario runner.
- **Only the agent and the webhook receipt are stood in.** The webhook receipt is `exec.on_payment_paid(razorpay_ref)` — the exact code the HMAC-verified webhook handler runs — so nothing on the money path is mocked. The payment link is a REAL test-mode object; in the live venue the real `payment_link.paid` webhook fires instead.
- **Added a `cart_built` audit event to `storefront.create_cart`** so the end-to-end chain is complete: `session_created → cart_built → gate_decision → token_issued → payment_effect(pending) → payment_effect(success)`. `session_created` is appended by the caller at delegation (the agent takes this over in Phase 6).
- **Reliability:** runs cleanly twice in a row (fresh session + real link each run; `verify_chain` PASS both times).

## Phase 6 — Buyer agent + agentic pipeline (Python)

- **Gemini API key format:** the key is an AI Studio API key used via `?key=` (NOT an OAuth Bearer token). Model `gemini-flash-latest` (a stable alias; `gemini-2.0-flash` is retired). Added a retry (429/500/503) for transient API errors.
- **checkout triggers execution server-side.** Refactored `ExecutionPlane` to hold `Arc<dyn PaymentGateway>` (was generic) so it embeds in the storefront; `Storefront::with_execution` makes an approved `checkout` create the real payment link. The agent therefore has NO money tool — `checkout` is its only spending path, fully kernel-gated (the ACP merchant→PSP pattern). Gate-only `Storefront::new` is kept for the Phase 3 tests and the walking skeleton.
- **AFA human-approval resume:** added `afa_approved` to the kernel input + `checkout`; the orchestrator's `approve()` re-runs checkout with it true to clear the ₹15,000 gate (all other bounds still enforced).
- **Bounded shopper:** the Discovery worker filters search results to the mandate's allowed category + merchant *before* proposing — so the agent shops only buyable items (the kernel remains the gate). Required adding `merchant_id` to the catalog search view.
- **Search upgraded to Postgres full-text** (`plainto_tsquery` + `ts_rank`, ILIKE fallback) so "running shoes" matches "Running Shoe" (stemming). The Phase 7 trained ranker swaps in behind the same tool.
- **Dependency-injected orchestrator** (llm/mcp/db) so the safety properties are unit-testable with fakes — no live LLM/server/DB needed in CI: zero-LLM-before-precheck, ambiguous→clarify, needs-human pause+resume, and "workers cannot call checkout" (runtime guardrail + source-level structural test).

## Phase 7 — Relevance / upsell / confidence ML

- **Relevance ranker (Amazon ESCI):** XGBoost over [MiniLM semantic cosine + lexical overlap + length] features, trained on ESCI-US graded labels (E/S/C/I → 3/2/1/0). Held-out **NDCG@10 0.9096 → 0.9202 (+1.2%)** over a keyword baseline — a real gain on an already-strong baseline (ESCI queries/titles share vocabulary). Reranks the storefront's candidate results inside the Discovery worker.
- **Upsell (all three sources):** Instacart Market-Basket → product/aisle 'bought-together' via lift (classic pairs: bananas+strawberries ×2384); Amazon **ESCI-C** → 40,049 explicit complement pairs; **Amazon Reviews 2023** → user **co-review** category complements on Clothing/Shoes/Jewelry (1402 categories, 582 complement keys). Combined into a category→complement-category table the Cart-Composer applies over the live catalog (same-merchant, in-budget, mandate-allowed category).
- **Amazon Reviews 2023 honesty:** the 2023 release DROPPED the `also_bought`/`bought_together` co-purchase fields (they existed in 2018), and the Amazon_Fashion meta has no sub-taxonomy — so those yielded nothing. We instead derive complements from real **user co-review** on the Clothing/Shoes/Jewelry split (which has a sub-category taxonomy). Documented; the HF loading script is also deprecated, so we stream McAuley's direct jsonl.gz.
- **Purchase Confidence Scorer:** gradient-boosted classifier over 5 named features (cart-to-goal match, price variance, category ambiguity, clarification turns, upsell acceptance), trained on **synthesised** clear/ambiguous scenarios (stated openly). Replaces the heuristic 'low confidence' with a deterministic, inspectable signal; below threshold routes to NEEDS_HUMAN **citing the scorer**, same footing as the ₹15,000 AFA rule.
- **Serving = in-process** (the plan explicitly allows this over a network hop): the agent loads the three joblib artifacts best-effort at startup; if any is missing it falls back to heuristics (so CI, which does not train, and all unit tests stay green). Model artifacts (`*.joblib`) and datasets (`data/raw/`) are git-ignored and reproduced by the `train.py` scripts.
- **CPU PyTorch** (not CUDA): the sampled ESCI subset + small GBMs train in minutes; the GPU would only speed embedding, which isn't the bottleneck at this scale.

## Phase 8 — Durable workflow spine

- **Temporal (Python SDK) drives the durable workflow; Rust services are activities** invoked over HTTP (the MCP checkout). Chosen over Restate because Temporal's Python SDK is GA while the Rust SDK is public-preview (the prompt's recommended split).
- **The NEEDS_HUMAN wait and the mandate-TTL are both durable:** `workflow.wait_condition(lambda: approved, timeout=ttl)` — the approval signal resumes it, the TTL timeout revokes it. State lives in the Temporal server, so killing + restarting the worker mid-wait resumes exactly where it left off.
- **No double-execution across a crash:** the `authorize_payment` activity goes through the idempotent execution plane (`ON CONFLICT`), so a retry after a crash returns the same payment link. Verified: after kill → restart → approve, the session has exactly **1 payment_effect**.
- **TTL expiry → session REVOKED** (the authority ended before approval).
- **Sync activities run via a `ThreadPoolExecutor`:** the activities use `requests`/`psycopg` (blocking), and Temporal requires an `activity_executor` for non-async activities (caught at runtime — the async test mocks had hidden it).
- **Temporal behind the compose `workflow` profile** (opt-in); its `auto-setup` image creates the temporal databases in the app Postgres.
- **Tests use `WorkflowEnvironment` time-skipping with mocked activities** (deterministic, no external Temporal/storefront/DB); they skip if the test server can't start, so CI stays green.

## Phase 9 — Explanation & audit narrative

- **The narrator DESCRIBES, never decides.** `services/explain/narrator.py` is fed each already-made decision (event type + payload) and returns a one-sentence description via the LLM; it cannot change a money outcome. The system prompt is explicit ("DESCRIBE ONLY — never approve, change, re-judge").
- **Narrative is a non-hashed field.** The hash covers `prev_hash || payload || event_type || ts` — NOT `narrative` — so writing narratives after the fact never breaks `verify_chain` (confirmed live: `verified: True` after narration). Decision and narration are separate persisted artifacts.
- **Gateway read API `GET /sessions/{id}/audit`** returns the full narrated, hash-verified chain (`verified`, `entry_count`, `entries[]` with seq/event_type/hashes/payload/narrative/ts) — the read surface the frontend audit viewer consumes. Required adding the DB pool to `AppState`.
- **Structured LLM output:** the narrator uses `complete_json` returning `{"narrative": "..."}` (robust vs. free-text parsing). Narratives are generated once and stored, so the read path never depends on the LLM.

## Phase 10 — Observability, security & hardening

- **Money-path tracing spans:** added `#[instrument]` spans to `storefront.checkout`, `storefront.create_cart`, `execution.authorize`, and `razorpay.create_payment_link`, so a checkout is one coherent trace in Grafana/Tempo (MCP → kernel-gated checkout → execution → the real Razorpay call). All services export OTLP.
- **W3C trace propagation across languages:** the global `TraceContextPropagator` is set in every service; the Python agent auto-injects `traceparent` (RequestsInstrumentor) into the MCP calls, and the storefront extracts it. Verified over the wire (the storefront receives the agent's trace id). **Honest limitation:** `tracing-opentelemetry`'s `set_parent` did not group the Rust spans under the agent's trace id in this version — both services' spans are in Grafana and the context is propagated, but the single cross-language trace grouping is a known nuance left as polish.
- **Delegated token is single-use (DB-enforced):** `UNIQUE(delegated_token)` on `payment_effect` makes token reuse a hard error, proven by a test.
- **Webhook replay protection:** every delivered body is recorded once (`webhook_event`, SHA-256 PK); a replayed/duplicate delivery is acknowledged (200) but not re-processed. Proven by a test. HMAC is still verified over the RAW body on every call.
- **Rate limiting:** a dependency-free global token-bucket middleware on the gateway (200 burst, 200/s) returns 429 when exceeded.
- **Secrets:** manual scan (`git grep`) confirms no real keys in tracked files — only placeholders in `.env.example`; `.env` and any key files are git-ignored; the ed25519 signing key is generated ephemerally (never persisted/committed).
- **LLM resilience (bonus):** the agent falls back to a deterministic regex intent-parse when the LLM is unavailable (rate-limited/outage), so a purchase still proceeds — the kernel and mandate bounds still gate everything.

## Durable, DB-backed console run history (2026-08-28)

Context: the shopping console's cart list lived only in React `useState`, so switching tabs (or reloading) wiped it. First pass persisted it to `localStorage`; then the user asked whether the runs/transactions should live in the database for durable, cross-device logs. They chose **full DB-backed history**.

- **The authoritative transaction/audit records were ALREADY in Postgres** (`cart_mandate`, `gate_decision`, `payment_effect`, hash-chained `audit_entry`) and surfaced via `GET /sessions/{id}/audit`. The console's cart list was only a **UI presentation cache** (goal text + stepper + display grouping) — that part is legitimately per-browser.
- **Rejected: one session per run.** Spend accumulates per `purchase_session` and the kernel's budget check reads `session.running_spend_paise` — that's *why* the console reuses one session per mandate (total-budget enforcement holds across runs). Making each run its own session would have forced spend-aggregation into the security-critical kernel path. Not worth destabilizing the money model for a UI feature.
- **Chosen: a first-class `agent_run` read model** (migration `0005_runs.sql`). One durable row per run, referencing the SHARED session, storing the goal text + the full `OrchestratorResult` snapshot (JSONB) for a faithful UI rebuild. A run is explicitly **not** a session; the budget model is untouched.
- **Who writes it:** the Python agent API (`db.record_run`, upsert keyed by a client `run_id` stable across a run's run→select→approve steps). This is the one write from the agent side — an **append-only orchestration LOG**, not a money/state mutation (those still go only through the Rust/kernel path). It must be, because CLARIFY/CHOOSE/pre-check runs terminate in the orchestrator and never reach Rust checkout, so only Python sees their outcome. Best-effort: a logging failure never breaks the user's run.
- **Who reads it:** the Rust gateway — `GET /mandates/{id}/runs` (list, newest-first) and `DELETE /mandates/{id}/runs/{run_id}`, both **owner-scoped exactly like the other `/mandates` routes**. Read/delete/ownership proven by `crates/gateway/tests/runs_api_tests.rs`.
- **Frontend:** `ShopPage` paints instantly from the localStorage cache, then reconciles against the DB, merging by `run_id` (server wins; cache-only/in-flight cards preserved, never wiped on a backend hiccup). `localStorage` is now just a fast cache; the DB is the source of truth, so history follows the user across devices and cache clears.

## Embedding-based upsell matching (2026-08-28)

The upsell model IS genuinely wired end-to-end (ml_loader.load_upsell → Orchestrator → CartComposer → find_upsell → the same object's methods → OrchestratorResult.upsell_suggestion → the UI's UpsellPrompt). But its matching was exact category-string lookup, and the trained co-purchase table's category vocabulary (Instacart grocery aisles + Amazon Reviews fashion) barely overlaps this deployment's live catalog (a general 325-category Amazon marketplace export). That's why a hand-curated overlay was needed for the demo categories.

Upgraded matching to embeddings — the same MiniLM/pgvector machinery search already uses — so the co-purchase signal generalises instead of needing exact string matches on two axes:

- **Chosen category → trained key** (`UpsellModel.complement_categories_for`): an exact table hit wins; otherwise the complements of the semantically NEAREST trained key are used, gated by a cosine `min_similarity` (0.55). So an unseen catalog category (`luggage`, `safety supply`) still gets a real, co-purchase-derived complement, and something with no close key (`clock`) honestly gets nothing.
- **Complement concept → live catalog** (`CartComposer.find_upsell`): each complement category now drives the storefront's SEMANTIC search (passes `query_embedding`, like discovery does) instead of requiring an item whose category string exactly equals the complement — so 'socks' matches the nearest real product even when no category is literally named 'socks'. The mandate is still enforced on the RETURNED item's real category, and a complement must be a DIFFERENT category than the chosen item.

One shared MiniLM embedder across the pipeline: the relevance ranker owns it (lazy-loaded), and the orchestrator injects it into the upsell model (`set_embedder(relevance.embedder)`) so both speak the same embedding space and MiniLM is never loaded twice.

**Honest tradeoff:** broader coverage, variable quality. The curated/exact pairs still give the cleanest suggestions (ring→earring, sofa→rug); the semantic fallback fills gaps with best-effort matches whose quality depends on the similarity threshold and the (sometimes noisy) category the catalog assigned the chosen item. This is strictly more general than exact-string matching and consistent with how search already works.

## Spend commits at authorization, not on payment-confirmation webhook (2026-08-28)

The user noticed the spend meter stayed at 0% after a purchase was approved and a payment link issued. Root cause: `running_spend_paise` only updated in `ExecutionPlane::on_payment_paid` — fired by a verified `payment_link.paid` Razorpay webhook. This product's actual flow stops at "here's your payment link" (nobody is obligated to click through and pay), so that webhook essentially never fires in normal use. Consequence: the kernel's cumulative-budget check (`running_spend_paise + cart.total > budget_total`) was reading a value that never moved — the agent could get approved for purchase after purchase in one session with the total silently exceeding the mandate's budget, since only a genuinely-paid purchase ever counted. This directly undermined the kernel's own cumulative-cap guarantee, not just a UI cosmetic issue.

**Fix — an authorization hold, same as a credit card:** `running_spend_paise` now commits in `ExecutionPlane::authorize()`, the instant the kernel approves and a payment link is issued — before any webhook. `on_payment_paid` no longer touches it (already committed, would double-count). `on_payment_failed` now releases the hold (decrements it back), since the money never moved. This is the exact "authorization hold reduces available credit before settlement" model real card networks use, and it's also what the schema's already-unused `reserve_block` table gestures at (never wired up; this fix achieves the same effect through the field already read everywhere — `purchase_session.running_spend_paise` — rather than adding a second source of truth).

Because the kernel already reads this same field for every subsequent purchase in a session, "remembering it for further shopping" required no separate wiring — moving WHEN it's written was the whole fix.

**Verified:**
- `crates/execution/tests/execution_tests.rs`: 3 tests — commits at authorize (not webhook), no double-count on payment_paid, hold releases on payment_failed.

## Audit grouping bug, root-caused: two different clocks (2026-08-30)

A user report ("the previous bought product's log is also showing in the current") turned out to be a real, still-live bug in the audit-trail-by-cart grouping the earlier "merging unrelated purchases" fix (`cd35055`, 2026-08-27) had put in place: `attributeTimestampToRun` (`frontend/src/lib/auditGrouping.ts`) attributes each `audit_entry` to a run by checking whether its `ts` falls inside that run's `[created_at, updated_at]` window (from `agent_run`, set by the Python API via SQL `now()`). When an entry's `ts` fell just outside every window, the old fallback attached it to **the newest run in the whole mandate** — so a run's own late-stage entries (`token_issued`, `payment_effect`, occasionally `gate_decision`) that landed a few hundred ms past their own run's `updated_at` got dumped onto a completely unrelated, later cart. Confirmed against the exact production data from the report: a `REFUSED ₹21,232` gate_decision and a `token_issued`/`payment_effect ₹1,848` pair, both from OLDER runs, were showing inside a newer `AUTHORIZED ₹3,656` cart's story.

**Root cause, measured, not guessed:** `crates/ledger/src/audit.rs`'s `append()` stamped `ts` from `OffsetDateTime::now_utc()` — the **Rust process's host clock** — while Python's `agent_run.updated_at` comes from Postgres's own `now()`. A direct query of `SELECT now()` against the DB vs. the host clock at the same instant showed **~1.3s of drift** (Postgres, containerized, running measurably ahead/behind the host at different times) — enough to occasionally push a run's own final audit writes just past the window Python had already recorded for it moments earlier.

**Fix, at the source:** `append()` now sources `ts` from Postgres too (`SELECT now()` inside the same transaction as the insert, so the hash — which is computed over `ts_micros(ts)` — still binds a value known before the row is written). Both `audit_entry.ts` and `agent_run.updated_at` now share exactly one clock, so the window comparison is meaningful again. Regenerated `.sqlx` offline cache (`cargo sqlx prepare --workspace -- --all-targets`) for the new query — the diff picked up 3 other legitimate, previously-uncaptured test-only queries alongside it, nothing removed.

**Fix, defense-in-depth (frontend):** `attributeTimestampToRun` no longer treats "no exact window match" as all-or-nothing (earliest/latest run in the whole list) — it now attaches an orphaned timestamp to whichever run's window is **temporally nearest**, by distance to the closer edge. This is what actually fixes the user's ALREADY-RECORDED historical data (the backend fix only prevents new drift going forward; old rows keep their already-drifted `ts` forever) — re-run against the exact real timestamps from the report, all three orphaned entries now correctly land back on their true run instead of the newest one in the mandate.

**Verified:** full Rust workspace test suite (59 tests, 0 failed, including the 8 ledger hash-chain tests — tamper detection still works with the new ts source) + clippy `-D warnings` clean + `cargo fmt --check` clean on the changed file + offline (`SQLX_OFFLINE=true`) build clean. 2 new + 5 existing frontend `auditGrouping.test.ts` tests (7/7) — the new tests reproduce the exact bug (a near-miss past an earlier run's window must attach to that run, not the newest one) and confirm a genuinely closer later run still wins over a further-away earlier one. Full frontend suite 33/33, `tsc` clean. Live: measured the real host-vs-Postgres drift (1.294s) before the fix; ran a fresh end-to-end purchase after rebuilding — `token_issued`/`payment_effect` now land ~17-25ms *before* their run's `updated_at` (correct ordering) instead of ~500-800ms *after* it (the bug). Re-computed the new nearest-distance algorithm directly against the real historical rows from the report — all three previously-misattributed entries now resolve to their correct run.

## Multi-product goals: "buy running shoes and a phone case" (2026-08-30)

Reported live: a goal naming two distinct products only ever produced a cart with one of them — `Intent` (`services/agent/models.py`) held exactly one `query`/`category`/`max_price_paise`, so the LLM parse always collapsed a multi-product request down to a single search. The cart/kernel/audit/execution layers never needed a change — `create_cart` already takes a list of items and the kernel's `check_categories`/cart-integrity checks already iterate every line item (`crates/kernel/src/lib.rs`); the gap was entirely in how the agent parsed and resolved a goal, one product at a time.

**Design.** `_parse_items` (replacing `_parse_intent`) returns one `Intent` per distinct product the LLM finds in the goal — a whole-request ambiguity ("something nice") still collapses to a single ambiguous `Intent`, so the existing CLARIFY check is unchanged. A new `_resolve_items` loop (`orchestrator.py`) walks the list: a product with exactly one real match auto-continues (no human input needed when there's only one real answer — the "agent never guesses" principle is about choosing *among* options, not about needing a human for every step); a product with several matches pauses the *whole* request at CHOOSE (`"Item 2 of 3: ..."`), carrying already-resolved products forward via `pending_items`/`resolved_items` on `OrchestratorResult` — plain dicts the client echoes back on `POST /select`, since the orchestrator has no memory of its own between HTTP calls (same shape as the UPSELL flow's `cart_id`/`item_id` round-trip). A product with no match aborts the *whole* request cleanly — never a cart with only some of what was asked for. Once every product resolves, `CartComposer.compose_many` (additive — the original single-item `compose()` is untouched, so its 10 existing tests needed zero changes) builds one cart from all of them; the confidence gate and upsell are both skipped for a multi-product cart, for the same reason `select()` already skips the confidence gate on an explicit human pick — an already-resolved product (auto-matched or human-chosen) is a stronger signal than a heuristic score, and offering an upsell would mean guessing which *one* of several items to pair it with.

**A real second bug found via live testing, not speculation:** `create_cart` enforces single-merchant carts (this catalog seeds items across more than one merchant, not just the one named on the mandate form). The first version of this fix let a human pick two incompatible items and only found out from `create_cart`'s raw error — a real regression against "graceful failure is a first-class path." Fixed at the root: `_resolve_items` now scopes every subsequent product's search to the merchant of whatever's already resolved (the same precedent `find_upsell` already set for single-merchant complements), so an incompatible option is never even offered — the human sees a clean, deterministic, zero-LLM-call explanation instead of a raw tool error. `_compose_and_checkout_many` also re-checks defensively before ever calling `create_cart`, for the one path that bypasses `_resolve_items`'s scoping: a client echoing back stale `resolved_items` from before this fix shipped.

**Verified:** 6 new orchestrator tests (unambiguous multi-item composes one cart in a single call; pauses at CHOOSE for the second ambiguous product while carrying the first forward; `select()` continues that exchange into one cart; a no-match on the second product aborts cleanly with nothing added; the real LLM-parse path splits a goal via a scripted multi-item response; the single-merchant regression — a second product only available from a different seller is refused before `create_cart`, not after) + all 21 pre-existing orchestrator tests unchanged + full python suite (63) + ruff clean + frontend `tsc`/vitest (33) clean. Live end-to-end, twice: first reproduced the exact reported bug and the single-merchant raw-error regression it exposed, then — after the merchant-scoping fix — a real purchase, **"buy a phone case and running shoes"** → CHOOSE for the phone case → CHOOSE for running shoes (correctly scoped to the same merchant) → **one cart, 2 line items, ₹5,537, gated as a single kernel decision against the ₹6,000 per-txn cap** → AUTHORIZED with a real Razorpay payment link.

## Multi-product: ask for every item, not just the ambiguous ones (2026-08-30)

Reported live right after the fix above shipped: item 1 of a multi-product goal correctly paused at CHOOSE, but item 2+ sometimes silently resolved without ever asking. Root cause was the *previous* fix's own merchant-scoping: once item 1 resolves, every later item's search is scoped to that same merchant (so an incompatible pick is caught before `create_cart` rather than after) — and scoping a search down to one specific merchant can legitimately narrow a product that had several real options in the *whole* catalog down to exactly one *within that merchant*. The original design auto-continued past any single-candidate item (no ambiguity, nothing to decide) — reasonable for a standalone single-product goal, but wrong here: the human never saw that the option pool had just been invisibly narrowed by a constraint (single-merchant carts) they don't know exists, and it was added to a cart charging them for it without confirmation.

Confirmed by checking the actual seed data: the catalog has **5 distinct merchants** (two carrying the full 1,000-item catalog, three carrying 250–400 items each) — not the single "Paybound Demo Store" the mandate form implies, so this narrowing is a routine occurrence, not an edge case.

**Fix:** `_resolve_items` now computes once, over the whole exchange, whether this is a genuinely multi-product goal (`is_multi_product = (len(resolved) + len(remaining)) > 1`). For a multi-product goal, EVERY item pauses at CHOOSE — even with exactly one candidate — so a human explicitly confirms each line item of a cart that charges them together, rather than trusting an invisible narrowing. A single-product goal keeps its original behavior unchanged (auto-resolves on one unambiguous match — no second product's cart-sharing risk to guard against). Also fixed the "I found 1 options" grammar bug this made newly reachable.

**Verified:** rewrote the 4 multi-item tests whose assertions assumed the old auto-continue behavior (each now steps through every CHOOSE explicitly, matching what a real client does) + added no new test count change, still 27 orchestrator / 63 full suite, ruff clean. Live: reproduced the exact reported gap directly against the real catalog — a goal picking a headphone-adjacent item from a smaller merchant (3621fef3, 400 items), then confirmed item 2 ("phone case") now returns `CHOOSE` with `"I found 1 option ... — which would you like?"` instead of silently resolving — then completed the pick end-to-end to a real `AUTHORIZED` cart with both items (₹7,608) and a real Razorpay payment link.
